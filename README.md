# TGPan · 把 Telegram 频道变成无限云盘

一个 Docker 镜像搞定：**TG 频道 → 网盘界面 → 在线看片 → WebDAV 挂播放器**。

> 支持 `amd64` / `arm64`，**任何设备 / 任何服务器 / 任何系统都能跑**：甲骨文 ARM 免费机、飞牛 OS、斐讯 N1 盒子、群晖、威联通、x86 小主机、VPS 一律通用。不挑内网外网，不认域名，不做端口绑定。

## 2.7.2 修了什么：电视盒子 / 低配设备上不再「打不开网页、反复重启」

### 你遇到的现象

在**斐讯 N1 盒子**（ARM64、2GB 内存、eMMC 存储）上装容器，反复出现：

- **网页打不开**（容器在跑，就是打不开）
- 界面上**冒出 5432 端口**（见 2.7.1，装的是旧版镜像）
- 容器**各种崩溃、反复重启**

排查后确认：**全部出在项目自己的代码和启动脚本上**，与设备内存/CPU 无关。
共 7 处缺陷，逐一修掉。

### 修了什么

| # | 位置 | 问题 | 现在的行为 |
|---|---|---|---|
| 1 | `run.go` | **端口被占就静默换号**：发现 8080 被占就自己跑 8081，只打一条不容易注意的日志 | **直接绑定，绑不上就明确报错退出**，日志里写清原因和处理办法 |
| 2 | `run.go` | **数据库连不上就 `os.Exit(1)`**：PG 还在初始化时进程直接死 → supervisord 拉起 → 又死……无限循环 | **拿着端口等 DB 就绪**，不再退出，DB 一好立刻可用 |
| 3 | `run.go` | cron / 事件 / redis 等**后台服务失败也 `os.Exit(1)`**，一个定时任务没起来就把整个进程干掉 | 记一条醒目错误日志，**继续运行**（这些都不影响打开网页） |
| 4 | `internal_database_database.go` | DB 连接只重试 5 次 × 500ms ≈ **2.5 秒**，盒子慢的时候根本不够 | 60 次 + **指数退避**（0.5→1→2→4→4…s，约 90 秒窗口） |
| 5 | `internal_database_tuning.go` | `work_mem` 写死 16MB，小内存设备上反而成负担 | 按可用内存**自适应**：≤1GB→4MB、≤2GB→8MB、>2GB→16MB |
| 6 | `docker/entrypoint.sh` | initdb **只判断 `PG_VERSION`**，中途失败留下残缺目录，下次误以为已完成 → 反复崩 | 加判 `global/pg_control`；残缺目录移到 `.broken.<时间戳>` 重来 |
| 7 | `docker/supervisord.conf`<br>`docker/teldrive-entry.sh` | 两套 PG 初始化脚本**互相打架**（pgroonga 入口脚本会改权限、重启自己）；supervisord 默认只重试 3 次，失败后标 FATAL 永不再拉起 | supervisord 直接调 `postgres`；`startretries=100`；等 DB 时间 60→120 秒 |

### 最关键的两条

**一、端口绝不能"静默换号"**

容器里端口映射是**写死**的（`-p 8080:8080`）。程序发现 8080 被占就自己跑 8081，
映射关系当场断掉 —— 表现就是「容器在跑、日志正常、网页打不开」，几乎没法排查。

```go
func listenOnConfiguredPort(port int) (net.Listener, error) {
    ln, err := net.Listen("tcp", fmt.Sprintf(":%d", port))
    if err != nil {
        return nil, fmt.Errorf(
            "无法监听端口 %d：%w\n"+
                "       常见原因：该端口已被占用（比如上一次的容器没退干净）。\n"+
                "       处理：改掉占用它的进程，或在宿主机上换一个映射端口（如 -p 18080:8080 后填 8080）。",
            port, err)
    }
    return ln, nil
}
```

报错长这样（**直接告诉你怎么办**，不用去猜）：
```
✗ ERROR [APP] server.port_unavailable
  error=无法监听端口 8080：listen tcp :8080: bind: address already in use
        常见原因：该端口已被占用（比如上一次的容器没退干净）。
        处理：改掉占用它的进程，或在宿主机上换一个映射端口（如 -p 18080:8080 后填 8080）。
```

**二、数据库没就绪时要"拿着端口等"，不要退出**

同容器部署时 Postgres 和 TGPan 是**并行拉起**的。盒子 eMMC 慢，
PG 首次启动要 initdb + 建 14 张表 + 建 pgroonga 扩展，几十秒很正常。
旧逻辑连不上就退出 → supervisord 拉起 → 又连不上 → 又退出，无限循环。

现在改成循环等待，日志清晰可见：
```
✓ INFO [APP] server.listening      port=8080
⚠ WARN [APP] db.connection.failed  attempt=1 max_retries=61 retry_in=500ms
⚠ WARN [APP] db.connection.failed  attempt=2 max_retries=61 retry_in=1s
⚠ WARN [APP] db.connection.failed  attempt=3 max_retries=61 retry_in=2s
⚠ WARN [APP] db.connection.failed  attempt=4 max_retries=61 retry_in=4s
✓ INFO [APP] db.ready_after_waiting rounds=2        ← DB 一好就自动继续，不用重启
```

### 实测验证

在真实二进制上（amd64）跑的两组端到端验证：

| 场景 | 期望 | 实测结果 |
|---|---|---|
| 8080 空闲、数据库未就绪 | 端口绑上、**进程不退出**、指数退避重试 | ✅ `server.listening`，12 秒内 `attempt=1..6`，进程存活 |
| 8080 被占用 | 明确报错退出、**绝不换端口** | ✅ 退出码 1、`server.port_unavailable`、确认未绑 8081 |

另附 3 个单元测试（`cmd/run_port_test.go`）钉住"端口占用必须报错"，
防止以后有人又把它改回"静默换号"。

> **如果你之前装的是 2.7.1 或更早**：镜像里还带着 pgroonga 继承来的
> 5432 端口和第二个挂载点，那就是你看到"去连 5342"（实为 5432）的原因。
> 拉 2.7.2 后这两个多余项都没了。

## 2.7.1 修了什么：新建容器时不再被逼着填多余项

### 你遇到的现象

在飞牛（或群晖、极空间等任何 NAS）里**创建容器**，表单会自动冒出：

- **两个存储挂载** —— 除了该填的 `/data`，还多一个 `/var/lib/postgresql/data`
- **两个端口** —— 除了该填的 `8080`，还多一个 `5432`

每次新建都得手动清掉，很烦。**它们确实一点用都没有**：

| 多余项 | 实际用的 |
|---|---|
| 挂载 `/var/lib/postgresql/data` | 数据其实在 **`/data/postgres`** |
| 端口 `5432` | 数据库只监听 **`127.0.0.1`**，根本不对外 |

### 为什么会多出来

这两个不是我们写的，是**基础镜像自带的**。项目基于 `groonga/pgroonga`（PostgreSQL 的
全文搜索扩展版），它自己声明了那两条元数据。

麻烦的是：Docker 的 `VOLUME` 和 `EXPOSE` **只能加、不能删** ——
`FROM` 之后你写什么指令都撤销不掉从上游继承来的这两条。

### 怎么修掉的

**断开继承链**。不再直接 `FROM pgroonga`，改成三段式：

```dockerfile
FROM groonga/pgroonga:latest-alpine-17 AS dbsrc   # 只当素材
FROM alpine:3.24                                  # 干净的起点
COPY --from=dbsrc / /                             # 整个根文件系统搬过来
```

继承关系一断，pgroonga 那两条元数据就传不下来了。文件一个没少 ——
PostgreSQL 17.11、pgroonga 4.0.9、groonga 16.1.1 全都在。

### 效果

| 字段 | 改之前 | 改之后 |
|---|---|---|
| 挂载 | `/data` + `/var/lib/postgresql/data` | **只有 `/data`** |
| 端口 | `8080` + `5432` | **只有 `8080`** |

现在创建容器，表单里就只有该填的那一项。

### 自验

```bash
# 元数据：应只看到 /data 和 8080
docker inspect tianjian518/tgpan:2.7.1 --format '{{json .Config.Volumes}}'
docker inspect tianjian518/tgpan:2.7.1 --format '{{json .Config.ExposedPorts}}'
```

> ⚠️ **老版本升上来不用做任何事** —— 你原来映射的 `/data` 和 `8080` 原样继续用。
> 只是下次**新建**容器时少填两个框。

### 顺带调的参数

预取窗口默认值 `8` → `3`，`chunk-timeout` 30s → 20s。
详见下面 2.7.0 章节的「关于「加载十几秒」——先把账算清楚」，
`3` 这个值是实测出来的平衡点（4K 有富余、又不会把链路占满）。

## 2.7.0 新增了什么：不用再找频道 ID

### 解决什么问题

以前要扫一个频道，得先**自己想办法搞到频道 ID**：

- 把频道消息转发给 `@userinfobot` 问它要
- 或者手算 `t.me/c/...` 链接里的那串数字
- 加了一堆频道？那就一个个去问、一个个去填

**现在不用了**：打开「扫描」页，**你关注的频道全在列表里**，点一下「扫描」就行。

### 现在怎么工作

```
扫描页
┌──────────────────────────────────────────┐
│  ✅ 已扫描    电影天堂            [扫描]  │
│  ✅ 已扫描    美剧仓库            [扫描]  │
│  ⬜ 未扫描    纪录片频道          [扫描]  │
│  ⬜ 未扫描    某某影视频道        [扫描]  │
└──────────────────────────────────────────┘
```

- 进页面就自动加载，**不用填任何东西**
- 后台每 **30 分钟**自动同步一次你的频道列表（加频道、退频道都能跟上）
- 每个频道后面标着「已扫描 / 未扫描」和已导入的文件数
- 点「扫描」= **增量扫描**，只拉上次之后的新消息，不会从头翻一遍

### 手动刷新

列表右上角有「刷新」按钮，点一下**立刻去 TG 拉一次**（要等几秒）。
平时不用点，后台自己会同步。

### 顺带修的一个「慢」

播放器拖进度条时，之前那个「多路并发预取」被**首字节拖垮**了。
真机实测同一部 3984MB 的 mp4：

| 并发路数 | 首字节 | 吞吐 |
|---|---|---|
| **1 路** | **0.97s** | 0.71 MB/s |
| 4 路 | 13.34s | 1.19 MB/s |
| 8 路 | 26.45s | 0.60 MB/s |

并发越高起播越慢，8 路甚至比串行还慢（TG 对单账号限流 + 连接争抢）。

现在改成**滑动窗口**：**首窗口只发 1 个请求保证秒起播，第二轮之后才放大并发**。
两头的好处都要。

预取窗口数默认从 `8` **降到 `3`**（配置项 `[tg.stream]` → `prefetch-windows`）。
理由是这样的吞吐实测（单块 512KB、模拟网络延迟 600ms）：

| prefetch | 吞吐 |
|---|---|
| 1 | 1.66 MB/s |
| 2 | 3.13 MB/s |
| **3** | **4.44 MB/s** ← 默认 |
| 4 | 5.92 MB/s |
| 8 | 10.65 MB/s |

1080p 蓝光原盘码率大约 1.7 MB/s，**3 路给的 4.44 MB/s 已经两倍余量**。
再往上拉吞吐，代价是并发请求数线性上涨，而 TG 对单账号有速率限制 ——
实测 **8 路以上会触发限流，吞吐反而回落**，还把首字节一起拖慢。
`3` 是"够用 + 留余量给限流"的平衡点。

### 关于「加载十几秒」——先把账算清楚

很多人一看到慢就想改代码。**先看这一节，能省你几天白工。**

**第一个结论：延迟和 prefetch 无关。** 单测 (`internal/reader/timing_test.go`)
实测（模拟 800ms 单块往返）：

| 场景 | prefetch=1 | prefetch=8 |
|---|---|---|
| 首次打开首字节 | 800ms | **800ms** |
| 拖进度条后首字节 | 800ms | **800ms** |

**一模一样。** 因为首窗口恒发 1 个请求，prefetch 是在那之后才起作用的。
所以"能否加速起播"的答案从代码层面就是：**不能**。

**第二个结论：时间花在链路上。** 按你的部署
（爆米花 → Cloudflare → CF 隧道 → 甲骨文 → Telegram）逐段拆：

| 环节 | 耗时 | 代码能改吗 |
|---|---|---|
| 爆米花 → CF 边缘 | 1–3s | ❌ |
| CF 边缘 → 隧道回源 | 1–3s | ❌ |
| **CF 免费版对流媒体限速** | **2–8s** | ❌ ← 最大头 |
| 甲骨文 → TG | 0.3–1s | ❌ |
| 首个 1MB 下载 | 0.5–2s | ✅ 部分 |
| 播放器解封装 | 1–2s | ❌ |
| **合计** | **5.8–19s** | 只有 1 项能碰 |

**管理预期**：十几秒降到 8–10 秒是现实的；降到 3 秒不现实 ——
因为那 4.3–14 秒里的大部分，物理上就不在你能控制的地方。

### 流量走哪儿？（这是问得最多的问题）

按上面的架构，一次播放的字节要走**三遍**：

| 流量 | 走不走 | 说明 |
|---|---|---|
| **CF 隧道流量** | ✅ 走 | 免费版不限量，但**条款 2.8 禁止代理大量视频流**，量大被限速/警告 |
| **甲骨文出站流量** | ✅ 走 | 每月 10TB 免费额度，正常一个人看片远远用不完 |
| **甲骨文入站流量** | ✅ 走 | 入站免费，不计量 |

> **为什么不能绕过 CF 直连甲骨文？**
> 甲骨文那台机器**不能开放公网端口** —— 一开，公网扫段脚本几天内就会
> 扫到并植入挖矿木马。这是真实高频事故，不是危言耸听。
> 所以必须走 CF 隧道，**这个架构不能动**。
> 代价就是上面那张表：CF 免费版对视频流不友好，那 2–8 秒省不掉。

**能做的三件事**（都在你侧，不改代码）：

1. **CF 那侧的缓存规则**：给媒体文件的 Range 请求配 Cache Rule，
   命中边缘缓存就不回源，能省掉"边缘 → 隧道 → 甲骨文"那一整段。
2. **换 Cloudflare 的优选 IP**：爆米花 → CF 边缘那段 1–3s，很大一部分是
   边缘节点选得差。用优选 IP 工具挑一个延迟低的节点写进 DNS。
3. **接受它**：免费方案就是把钱换成时间。想要 3 秒起播，唯一的路是
   把片子放本地或者买个正经 CDN。

### 还调了数据库

批量导入和目录排序明显更快。三个参数直接写进连接串，
保证连接池里**每条新连接**都生效（不是只对一条连接生效）：

| 参数 | 值 | 为什么 |
|---|---|---|
| `synchronous_commit` | `off` | 批量导入不用等 WAL 落盘；崩溃最多丢最后几秒，重扫幂等 |
| `work_mem` | `16MB` | 目录排序不落盘做外部排序 |
| `jit` | `off` | 短查询上 JIT 编译开销大于收益 |

启动日志里可以确认生效：

```
INFO [APP] db.tuning.verify   synchronous_commit=off work_mem=16MB jit=off
```

> 默认开启。不想要就在配置里关：`[db]` → `tune = false`。

这一版重点做了自查，修掉了 7 个问题（都补了回归测试）。其中 3 个是**用户直接能撞上**的：

## 登录：扫码 / 验证码登一次，以后直接进

### 解决什么问题

以前每次打开 TGPan 都要扫码，而且有几个死结：

- 手机**扫不了自己屏幕上的二维码**（要扫的码就在手机里）
- 换个浏览器、换台设备就要重新扫
- 某些客户端/网络下发不出验证码

### 现在怎么工作

**登录就是登 TG，一步到位。** 没有第二套密码。

```
第一次打开
   └─▶ 页面显示登录页：扫码 或 手机验证码  ← 只做一次
         └─▶ 成功后凭证存在服务器，浏览器留一张门票
               └─▶ 完成

以后打开（同一个浏览器）
   └─▶ 直接进，不用再登
```

### 关键点

| 项目 | 说明 |
|---|---|
| **凭证存哪** | `/data/tgpan-gate.json`（TG 凭证 + 签名密钥），容器重启/重建/升级都不丢 |
| **要不要密码** | 不要。登录 = 登 TG，没有额外密码 |
| **要不要配域名** | 不要。内网、外网、域名、IP，行为完全一致 |
| **网址泄露了怎么办** | **进不去**。换浏览器打开只会看到登录页，见下 |
| **想换 TG 账号** | 点右下角「换账号」，或删 `/data/tgpan-gate.json` 重启 |

### 为什么网址被别人拿到也用不了

放行需要**同时**满足两个条件：

| 条件 | 是什么 | 证明什么 |
|---|---|---|
| ① 服务端有 TG 凭证 | 一次真实 TG 登录留下的 session | 「这个容器归谁」 |
| ② 浏览器有签名门票 | 登录成功时签发的一次性码换来的 Cookie | 「这个浏览器是主人」 |

只查 ① 会有一个致命漏洞：容器一旦登录过，**任何人拿到网址用任意浏览器打开都会被直接放进去** —— 等于没有登录。

所以门票这一层不能省。**这两个条件独立成立**，缺任何一个都只会看到登录页。

### 一次性领取码（Claim）

TG 登录完成在 WebSocket 里，升级握手后拿不到 `http.ResponseWriter`，没法直接 Set-Cookie。所以：

```
1. WS 登录成功 → 服务端生成一次性码，随成功消息发给前端
2. 前端拿码 → POST /gate/claim → 这一步是普通 HTTP，正常写 Cookie
```

码的安全属性：

- 32 字节随机（256 位），猜不出来
- 有效期 **60 秒**
- **用过即焚**，重放无效
- 绑定签发时的 `User-Agent`
- **不落盘**，进程重启即失效

### 状态

闸门只有两个状态：

| State | 含义 | 界面 |
|---|---|---|
| `need_login` | 服务端无凭证，**或**当前浏览器无门票 | 登录页（扫码 / 手机号两个 tab） |
| `ok` | 两者都有 | 主界面，右下角挂「换账号」浮标 |

### 接口

| 路径 | 方法 | 说明 |
|---|---|---|
| `/gate/status` | GET | 当前状态 |
| `/gate/claim` | POST | 用一次性码换门票 |
| `/gate/logout` | POST | 退出（清凭证 + 门票） |
| `/gate/repair` | POST | 换账号（等同退出） |

### 豁免路径（不拦）

| 路径 | 为什么 |
|---|---|
| `/version`、`/health` | 健康检查与前端探测，只暴露版本号 |
| `/auth/ws`、`/auth/session` | 登录 TG 本身，不豁免就登不进来 |
| `/webdav` 文件路径 | WebDAV 有自己的 Basic 认证；播放器挂载后发的 PROPFIND 带的是 Basic 凭据，被闸门拦成 401 会让客户端以为"密码错" |
| `/webdav/credentials` | **例外中的例外**：这是网页用的凭据管理接口，走登录态，必须拦 |

### 安全说明

- 门票是 HMAC-SHA256 签名，**不设 `Secure`**（内网 http 访问时设了会导致 Cookie 完全不保存）
- 闸门文件权限 `0600`，原子写入（先写临时文件再 rename），断电不会写坏
- 凭证是账号密钥，**只存服务端**，不放 Cookie（放 Cookie 等于把密钥交给客户端）

### 走过的弯路（别再改回去）

**弯路一：管理密码 + 内网免密 + 域名白名单。**
想法是"内网方便、外网安全"，实际结果：

- 配置里硬编码了作者自己的域名，别人部署时匹配不上 → **所有人免密直进**，设密码形同虚设
- 内网判断依赖 HTTP `Host`，而反代会改写 Host；Docker 网桥 / VPN / Tailscale 场景下"内网"边界很模糊
- 用户设完密码直接进主界面，TG 没配对 → 功能全 401 → 界面上还找不到配对入口，**彻底卡死**

根因：把「登录」和「配对」拆成了两件事。**其实它们就是一件事。**

**弯路二：自写 QR 编码器。**
用 jsQR 交叉验证，20 个用例**全挂**。逐层排查修了格式信息位序、纠错等级编码值、RS 生成多项式，还是不对。最后换成成熟库（`qrcode-generator`，MIT，被无数项目验证过），**20/20 通过**。

结论：编码器这种东西不要自己写。

## 2.6.0 新增了什么

这一版只干一件事：**让拖进度条不再卡十几秒**。

### 为什么以前会卡

在 TG 里看片，文件必须由服务器用 **MTProto 分块拉取**（每次 1MB），再转成 HTTP 流给你。
TG **官方不提供 HTTP 直链**，所以"服务器中转"这一步绕不开。

慢的地方在于：默认拉流用的是**你自己的 TG 账号**，而拖进度条时每次都要**重建一次账号连接**。
账号建连本身就慢，于是就有了那十几秒的等待。

### 现在怎么变快

配一个 **Telegram Bot**，改走 Bot 连接建流。Bot 建连比账号登录轻得多，所以明显快。

| | 以前 | 现在 |
|---|---|---|
| 建连方式 | 用户账号（要跑完整登录流程） | Bot（轻量） |
| 拖进度条等待 | 十几秒 | **约 2~5 秒** |

### 怎么配

1. TG 里找 **[@BotFather](https://t.me/BotFather)** → 发 `/newbot` → 起个名字
2. 它回你一串 `数字:字母` 形式的字符串，**那就是 Token**
3. 打开 TGPan 网页 → 右下角 **「🤖 Bot 加速」** 页签
4. 把 Token 粘进去（**一行一个，可以填多个**）→ 点「保存并加速」

填多个 Token 时，系统会**轮换使用**来分摊 TG 的限流，更稳。

### ⚠️ 一个必须说清楚的限制

**Bot 只能加速「你自己建的频道」。**

| 频道类型 | 能否加速 | 为什么 |
|---|---|---|
| 你自己建的频道（含从别处转发进来的） | ✅ 能 | 保存时后端会把这个 Bot 设为频道管理员，Bot 才有权取文件 |
| 别人的频道（你只是订阅） | ❌ 不能 | 你没权限把 Bot 加进别人的频道，加不进去 |

**但是**：加不进去**不影响正常播放**，只是回到原来的速度。保存后会逐个频道给出结果，失败的会说明原因，不会静默失败。

### 顺便修的一个挂载问题

播放器（爆米花 / Infuse / WinSCP / Windows 资源管理器）挂载前会先发一个**不带账号密码的探测请求**，
靠响应里的 `DAV` 头判断"对面到底是不是 WebDAV 服务器"。

以前这个头只在登录成功后才给，导致部分播放器**直接判定挂载失败，连密码框都不弹**。

现在改成：**401 响应里也带上 `DAV` / `Allow` / `Accept-Ranges` 三个头**，
同时保留标准的 `WWW-Authenticate` 质询。播放器拿到后会带着账号密码重试，这次就通过了。

> 安全性不受影响：未登录请求一个字节的文件内容都拿不到，只是多了几个能力声明头。

### 自验

```bash
go test ./pkg/services/     # 13 个单元测试，含 WebDAV 能力头与未授权防泄露
bash scripts/verify.sh      # 端到端：构建镜像 → 起容器 → 逐项检查
```

## 2.5.0 修了什么

这一版是**打磨版**：把项目从头到尾过了一遍，该堵的漏洞堵上、该修的 bug 修掉、界面提亮一档。功能没变，但用起来应该明显更顺眼、更稳。

### 安全

| 级别 | 问题 | 说明 |
|---|---|---|
| 🔴 **高** | **跨用户越权读取文件** | `/api/files/stream/{fileId}` 原来只校验「登录了没」，**不校验这个文件是不是你的**。任何人只要猜到/拿到一个 fileId，就能白嫖别人的片。现在查询强制带上 `user_id`，不是你的文件直接 404/401 |
| 🔴 **高** | **缓存跨用户串号** | 上面那个接口有缓存，缓存 key 原来不带用户维度。A 读过一次，B 请求同一个 id 会**命中 A 的缓存**，绕过鉴权。现在 key 里带上身份维度 |
| 🟡 中 | **扫描状态被别的用户覆盖** | `channel_scans` 表按 `channel_id` 查，没带 `user_id`。B 扫同一个频道会命中 A 的记录并覆盖，把 A 的游标和文件夹绑定串掉 |
| 🟡 中 | **WebDAV 账号能撞时序** | 用户名不存在时直接返回，存在的才跑 bcrypt。攻击者能靠响应快慢**枚举出哪些用户名是真的**。现在用户名不存在也跑一次假哈希 |
| 🟡 中 | **WebDAV 用户名仅靠代码查重** | 并发下两个请求可能同时通过检查。已在数据库层加唯一索引兜底 |
| 🟢 低 | **扫描翻页可能提前收工** | 原来用「处理了多少条」判断还有没有下一页，遇到服务消息/空消息会偏小，可能漏掉后面的视频。改用「本次实际拿到多少条」 |
| 🟢 低 | **JWT 签名算法未锁定** | 现在显式只接受 HMAC 族。（注：`jwt/v5` 本就默认拒绝 `alg=none`，这条属**纵深防御**，不是已暴露的漏洞——照实说明，不夸大） |

### 性能

- **剧集列表消除 N+1 查询** —— 原来「每个剧集文件夹查一次文件」，文件夹一多就是几十上百次数据库往返。改成一次 `IN` 查询后在内存分组，整体快一个量级。

### 界面与交互

| 修复 | 说明 |
|---|---|
| 空状态没样式 | 样式表里只写了 `#tgpan-empty`，但代码用的是 `.tgpan-empty`，class 写法一直没生效 |
| 暗色模式帮助块没配色 | 选择器写成 `#tgpan-help`，但元素是 class `.tgpan-help`，这条规则是死代码 |
| 输入框样式污染原版界面 | 一条裸的 `input, textarea, select{...}` 会把原版所有输入框的圆角一起改掉。已限定到自建弹窗内部 |
| 列表样式污染原版表格 | 表格化样式原来作用在全局 `tr` / `[role="row"]` 上，现在限定到文件列表容器内 |
| 数字属性没转义 | 频道 id 直接拼进 `data-*` 属性，已统一走转义 |
| 请求竞态 | 快速切页签时旧请求可能后到、覆盖新结果。三个列表都加了请求序号守卫 |

## 🔥 核心用法：把频道视频变成网盘文件

这是本项目**最实用的功能**。不需要下载、不需要上传、不吃你的带宽和硬盘。

**场景**：你 TG 里关注了一堆频道，里面有人发电影/剧集。你想直接在网盘里看。

**怎么做**：

1. 用小号登录 TGPan
2. 点右下角 **「📡 扫描 TG 频道」** 按钮
3. **在列表里找到那个频道，点「扫描」** —— 不用填 ID，列表里全是你关注的频道
4. 等几秒~几十秒，系统自动把这个频道里**所有视频**登记成网盘文件
5. 刷新页面 → 出现一个新文件夹 → 点开就能看 🎉

> ⚡ **原理**：只登记「索引」，不动文件本身。视频还在 TG 服务器上，播放时才实时拉流。
> 所以：**不占空间、不耗流量、秒完成**（消息多的话也就几十秒）。

### 列表里没有我要的频道？

说明这个 TG 小号还没关注它。去 TG 里关注/加入一下，
然后回扫描页点右上角「**刷新**」（或等 30 分钟自动同步）就有。

> ⚠️ **前提**：这个 TG 小号必须**已经加入**那个频道（公开频道点加入，私密频道要有人拉你进）。

### 还想手动填频道 ID？（保留能力）

列表是主要用法，但**接口依然支持手填**，方便脚本调用：

| 方法 | 操作 |
|---|---|
| **转发法** | 在 TG 里随便转发频道里的一条消息给 `@userinfobot`，它会回复频道 ID |
| **链接法** | 网页版频道链接形如 `t.me/c/1234567890/1`，中间那串数字就是 |
| **直接填** | `-1001234567890` 或 `1234567890` 都行，程序会自动处理 |

### 多个频道怎么办？

**重复扫描即可。** 每个频道扫一次，网盘里就多一个文件夹。

```
网盘根目录/
├── 📁 频道A-电影天堂/     ← 扫描频道A生成
├── 📁 频道B-美剧仓库/     ← 扫描频道B生成
├── 📁 频道C-纪录片/       ← 扫描频道C生成
└── 📁 我自己的文件/       ← 你自己上传的
```

重复扫描同一个频道**不会重复导入**（自动去重）。

## 🩺 登录卡住？先开这两个页面（不用终端）

### 1️⃣ 连接诊断：`/diag`

**地址：`http://你的IP:8080/diag`**（走隧道就是 `https://你的域名/diag`）

打开后会看到 5 项自动检测，每项带 ✅/❌ 和耗时：

| 检测项 | 说明 |
|---|---|
| **TG 应用凭据** | 检查内置的 api_id / app_hash 是否正常 |
| **DNS 解析 api.telegram.org** | 看域名解析结果对不对 |
| **对照：访问 core.telegram.org 网页** | 区分「整机没网」和「只有 TG 连不上」 |
| **TCP 直连 TG 数据中心** | 逐个测试 DC1/DC2/DC4/DC5 的 443 端口 |
| **MTProto 实际握手** | 真的连一次 TG，这是最终裁决 |

### 2️⃣ 登录链路自检：`/logincheck`

**地址：`http://你的IP:8080/logincheck`**

这个页面会**在服务器上真实跑一次「请求验证码」**，把每一步结果摊开：

| 步骤 | 说明 |
|---|---|
| 创建 TG 客户端 | 凭据有没有问题 |
| 连接 Telegram 服务器 | MTProto 握手成不成功 |
| **请求发送验证码** | **TG 到底回了什么**（错误原文会显示出来） |
| 取得 phoneCodeHash | 前端能不能拿到提交验证码所需的 hash |

> 想用自己的手机号测，加参数：`/logincheck?phone=+86138xxxxxxxx`
> ⚠️ 有 **60 秒节流**，因为它会真的向 TG 发一次验证码请求。

**结果怎么读：**

| 页面显示 | 含义 | 怎么办 |
|---|---|---|
| 全 ✅ | 服务器到 TG 完全正常 | 问题在前端或浏览器，截图发我 |
| TCP / 握手 ❌ | 服务器网络到不了 TG | 换能直连 TG 的网络／加代理 |
| 发码步骤 ❌ 有错误原文 | TG 明确拒绝了 | 把错误原文发我，这句话就是答案 |
| DNS 解析出奇怪 IP | 域名被 DNS 污染 | 换 DNS（如 `8.8.8.8`） |

> 加这两个页面的原因很直接：**原版登录界面在出错时一个字都不提示**，只让你看着 `Please Wait...` 无限转圈，谁都判断不出到底哪出了问题。

## 关键：Telegram 登录

**好消息：不用去 my.telegram.org 申请 api_id。**

镜像内置了公共应用凭据，你只需要：

| 登录方式 | 说明 |
|---|---|
| **二维码登录（推荐）** | 点 `QR Login` → 用手机 TG 扫一下 → 完成 |
| **手机号登录** | 填 `+86 你的号码` → 收验证码 → 完成 |

### ⚠️ 关于「验证码收不到」——先看这里

**Telegram 现在的策略是：验证码优先发到「你已登录的 Telegram 客户端」，而不是短信。**

诊断页会显示 TG 返回的类型：

| TG 返回类型 | 含义 | 验证码去哪了 |
|---|---|---|
| `auth.sentCodeTypeApp` | **通过 TG APP 下发**（最常见） | **打开 TG，搜官方账号 `Telegram`（蓝勾）**，验证码就在对话里 |
| `auth.sentCodeTypeSms` | 短信下发 | 看手机短信 |
| `auth.sentCodeTypeCall` | 电话语音播报 | 接电话听 |
| `auth.sentCodeTypeFlashCall` | 闪信 | 来电号码即验证码 |

> 💡 **如果验证码找不到，直接改用二维码登录。** 它不依赖验证码，用手机 TG 扫码即可，是最省事的路径。
>
> 二维码怎么扫：手机 TG → **设置 → 设备 → 扫描二维码**。

### 🔑 验证码死活收不到？换掉"网页版伪装"（v2.0.0）

**从 v2.0.0 起，支持在容器里填你自己的 TG 应用凭据，这是目前最有效的解法。**

**为什么有效**：Teldrive 原本把自己伪装成"Firefox 打开的网页版 Telegram"：

```
app-id       = 2496            # web.telegram.org 的共享凭据
device-model = Firefox/116.0   # 伪装成浏览器
lang-pack    = 'webk'          # WebK = 网页版内核
```

而 TG 官方文档明确：**网页版（WebK/WebA）不属于可接收验证码的客户端类型**。
所以 TG 会回你"已发出"（生成 hash），但验证码永远投递不到 —— 这正好解释
"每次都提示发出、却一次都收不到"。

v2.0.0 默认已改为**真实 Android 设备身份**，同时支持填入你自己的应用凭据。

**怎么填**：创建容器时，在**环境变量**里加两行（飞牛 OS 里就是"环境变量"输入框）：

```
TELDRIVE_TG_APP_ID=你的api_id
TELDRIVE_TG_APP_HASH=你的api_hash
```

`api_id` / `api_hash` 在 [my.telegram.org/apps](https://my.telegram.org/apps) 免费申请
（**用电脑浏览器打开**；手机浏览器对那个页面兼容性很差，容易报 ERROR）。
申请时 **URL 和 Description 不要留空**，Platform 选 Android。

> 不填也能跑（沿用内置默认值），但建议填上——它决定了 TG 是否愿意把验证码投给你。

**其他可选环境变量：**

| 变量 | 默认值 | 说明 |
|---|---|---|
| `TELDRIVE_TG_DEVICE_MODEL` | `SM-G9980` | 设备型号 |
| `TELDRIVE_TG_SYSTEM_VERSION` | `SDK 34` | 系统版本 |
| `TELDRIVE_TG_APP_VERSION` | `11.2.0` | 应用版本 |
| `TELDRIVE_TG_LANG_CODE` | `zh` | 语言代码 |
| `TELDRIVE_TG_LANG_PACK` | 空 | 语言包 |
| `TELDRIVE_TG_REAL_DEVICE` | `1` | 设为 `0` 关闭真实设备身份 |


> 💡 **建议用小号**。
> ⚠️ 官方警告：滥用 TG API 会**立即封号**；大量囤积文件会导致**频道被清空**。正常使用（看片、少量上传）没问题，别疯狂刷。

## 🔒 关于「换浏览器又要重新登录」

先说结论：**这不是 bug，是浏览器的本来就该有的行为。**

TGPan 的登录态存在浏览器 **Cookie** 里（`access_token`），不是存在服务器上。
所以：

| 场景 | 结果 | 为什么 |
|---|---|---|
| 同一个浏览器刷新页面 | ✅ 免登录 | Cookie 还在 |
| 同一个浏览器关掉再开 | ✅ 免登录 | Cookie 有效期默认 30 天（v2.2.0 起显式持久化） |
| **换一个浏览器** | ❌ 要重新登录 | 新浏览器里根本没有那个 Cookie |
| **换一台设备 / 换手机** | ❌ 要重新登录 | 同上 |

> 这跟你在电脑上登录淘宝，手机淘宝也得单独登录是**同一个道理**。
> 想让手机也能用，**在手机上单独扫一次码**即可，之后手机就一直免登录了。

### 两种提升便利性的办法

**办法一：把会话有效期调长**（默认已经 30 天，一般不用改）

```yaml
environment:
  - TELDRIVE_JWT_SESSION_TIME=365d
```

**办法二：用反向代理 + HTTPS 域名访问，并放宽 SameSite**

如果你发现"刚从微信/TG 里的链接点进来就要重新登录"，那是 `SameSite=Lax` 在跨站跳转时会拦 Cookie。改成 `none` 就好（注意：必须先有 **HTTPS**，HTTP 下浏览器会直接丢弃）：

```yaml
environment:
  - TELDRIVE_JWT_COOKIE_SAMESITE=none
```

## 挂载到播放器（WebDAV）

TGPan 内置了**独立的 WebDAV 服务端**，专门给播放器挂载用。

### 挂载地址

```
http://<你的内网IP>:8080/webdav
```

例如：`http://192.168.1.100:8080/webdav`

> ⚠️ 注意路径末尾是 `/webdav`，**不是** `/api/webdav`，也别只填 IP 不带路径。

### 账号密码从哪来

WebDAV 用的是**专用密码**，跟网页登录密码分开（更安全，也方便单独吊销）：

1. 打开 TGPan 网页 → 右下角 **「🔗 WebDAV」** 页签
2. 点「生成新凭据」→ 记下**用户名**和**密码**（密码只显示这一次，请立刻保存）
3. 播放器里就填这一对账号密码

### 各播放器怎么加

| 播放器 | 操作路径 |
|---|---|
| **网易爆米花** | 添加存储 → WebDAV → 填地址/账号/密码 |
| **Infuse** (iOS/Apple TV) | 添加文件来源 → WebDAV |
| **VidHub** (Apple 全家桶) | 添加 → WebDAV |
| **nPlayer** | 网络 → WebDAV |
| **Windows 资源管理器** | 映射网络驱动器 → 填 `http://IP:8080/webdav` |
| **PotPlayer** | 打开 → 远程连接 → WebDAV |

### WebDAV 里长什么样

```
/webdav/
├── 电影频道/            ← 一个 TG 频道 = 一个文件夹
│   ├── 流浪地球2 2023.mp4
│   └── 满江红 2023.mp4
└── 剧集频道/
    ├── 狂飙 01.mp4
    └── 狂飙 02.mp4
```

一个频道对应一个顶层文件夹，播放器刮削时目录结构清晰，容易识别。

### 支持的能力

| 能力 | 说明 |
|---|---|
| `OPTIONS` | 返回 `DAV: 1, 2` + `MS-Author-Via: DAV`（爆米花挂载探测必需） |
| `PROPFIND` | 列目录，标准 **207 Multi-Status** XML，中文名自动 URL 编码 |
| `GET` / `HEAD` | 拉流播放，**支持 HTTP Range** → 可以拖动进度条 |
| 认证 | HTTP Basic Auth + bcrypt 哈希存储 |

## 🔄 自动扫描频道（2 分钟一轮）

开启后**不用再手动扫**，频道里发新片会自动进网盘。

### 怎么开

1. 网页右下角 **「🔄 自动扫描」** 页签
2. 在频道列表里找到目标频道（列表自动加载，不用填 ID）→ 打开「**自动**」开关
3. 完成。之后每 **2 分钟**自动跑一轮

> 「自动扫描」列表来自后台每 **30 分钟**同步一次的「已关注频道」。
> 刚关注的新频道想立刻出现，点列表右上角「**刷新**」。

### 工作机制

| 特性 | 说明 |
|---|---|
| **增量扫描** | 记住上次扫到的消息位置，下轮只拉新消息，不重复处理 |
| **串行执行** | 多个频道排队跑，避免同时请求把 TG 配额打爆 |
| **指数退避** | 某轮失败后自动延长重试间隔（最长 1 小时），网络恢复后自动回到正常节奏 |
| **启动延迟** | 容器启动后等 45 秒再开始第一轮，确保 TG 连接池已就绪 |
| **不动原文件** | 只登记索引，视频仍在 TG 服务器，播放时才实时拉流 |

### 查看状态

「🔄 自动扫描」页签里能看到每个频道的：

- 上次扫描时间
- 已导入文件数
- 最近一次错误（如果有）

## 🎬 电视剧自动归档

扫频道时，系统会顺便看一眼每个视频的名字，认出是剧集就自动整理。

### 整理成什么样

假设频道里本来是这样一堆散片：

```
📁 某某影视频道/
   1.mp4                        （配文：狂飙 第05集）
   2.mp4                        （配文：狂飙 第06集）
   【某某压制】狂飙 第03集 1080p.mkv
   狂飙.S01E01.2160p.WEB-DL.mp4
   狂飙 第4集.mp4
   复仇者联盟4终局之战.2019.2160p.mp4
   2024年央视春晚.mp4
```

扫描后会变成：

```
📁 某某影视频道/
   📁 狂飙/
       狂飙 S01E01.mp4
       狂飙 S01E03.mkv
       狂飙 S01E04.mp4
       狂飙 S01E05.mp4
       狂飙 S01E06.mp4
   复仇者联盟4终局之战.2019.2160p.mp4     ← 电影，平铺不动
   2024年央视春晚.mp4                     ← 认不出，平铺不动
```

剧名文件夹挂在**频道文件夹底下**，所以频道 → 剧 → 集，树形很干净。WebDAV 挂到播放器后，刮削器看到 `狂飙/狂飙 S01E05.mp4` 这种结构，命中率最高。

### 设计原则：宁可漏判，不要错判

这是刻意选择的行为：

- **只有明确认出集数才归类**。`第05集`、`S01E05`、`EP05`、`05集`、`[06]` 都认
- **认不出来一律不动**。`狂飙 05.mp4` 这种只有数字结尾的**不认** —— 分不清它是第 5 集还是 2024 年还是别的
- **电影不会被误伤**。`复仇者联盟4终局之战`、`流浪地球2` 里的数字不会被当成集数

理由很直白：漏判只是少整理一次，文件平铺着照样能用；错判会把不相干的片子塞进同一个文件夹，比不整理更糟。

### 识别错了怎么改

「🎬 剧集」页签里能看到所有已识别的剧、收录到第几集、有没有缺集。

点「✏️ 改名 / 移动文件」可以：

- **改名** —— 把识别错的剧名改回来
- **移动** —— 把混进来的文件挪到别的文件夹，或挪回根目录

接口层还提供了文件夹合并（`POST /api/scan/series/merge`），用来处理同一部剧被拆成两个文件夹的情况（比如一半文件叫「狂飙」、另一半叫「狂飙 第二季」，识别出的剧名不同）。

### 相关接口

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/api/scan/series` | 列出所有剧集文件夹（剧名、集号范围、示例文件名） |
| `POST` | `/api/scan/series/rename` | 改名 / 移动一个文件 |
| `POST` | `/api/scan/series/merge` | 合并两个剧集文件夹 |

全部需要登录 Cookie，且只允许操作自己的文件（别人的 ID 一律返回 404，不泄露存在性）。

## 关于速度和卡顿

- **Teldrive 支持 302 直链**：播放器可以直连 TG 拿数据，不走你服务器带宽
- 但 TG 官方对个人账号有**限流**，频道文件特别多时首次加载会慢
- 建议：**保持默认的 `rate-limit = true`**（防封号），不要为了速度关掉

## 常见问题

**Q：打开 8080 没反应？**
等 30~60 秒（首次要初始化数据库）。还不行就看日志：
```bash
docker logs tgpan
```

**Q：日志报 `initdb: error: could not access directory "/data/postgres": Permission denied`？**

数据目录权限问题。新版镜像已自动处理，若仍出现，手动执行：
```bash
chmod 755 <你映射到 /data 的主机目录>
```
然后重启容器。

> 原因：容器里 postgres 用户要走进 `/data` 才能初始化数据库，
> 而挂载出来的目录通常 `mode 700`（只有 root 能进），把 postgres 挡在门外了。
> 注意：飞牛 NAS 的「文件权限」界面改的是它自己的 ACL，**不等于** Linux 的 mode，改那里没用。

**Q：登录时收不到验证码 / 一直卡在 `Please Wait...`？**

**请升级到 v1.2.0。** 新版会在出问题时**明确告诉你卡在哪**，而不是无限转圈：

| 界面提示 | 含义 | 怎么办 |
|---|---|---|
| `尚未连接到 Telegram，请稍候重试` | 服务器正在连 TG，或连不上 | 等几秒重试；一直这样说明**服务器到 Telegram 网络不通** |
| `连接 Telegram 失败：xxx` | 明确失败，括号里是原因 | 按错误内容排查（多为网络不通） |
| `已连接到 Telegram` | 连接正常 | 此时发验证码应该能收到 |
| 什么都没提示 | WebSocket 都没连上 | 检查反向代理是否支持 WebSocket |

**根本原因**：Teldrive 的登录通道先要连上 Telegram，连不上时它**既不报错也不返回**，
前端就只能一直等——这是原版的设计缺陷，v1.2.0 已修正为主动上报。

其他常见原因：
- 手机号要带国家码（`+86...`）
- 如果这个号之前登录过别处，TG 可能把验证码发到 **TG App 里**（搜 `Telegram` 官方对话）而不是短信
- 或者直接用**扫码登录**，最省事（不需要验证码）

**Q：扫描页的频道列表是空的 / 少了我刚加的频道？**

列表来自后台每 **30 分钟**同步一次你的 TG 频道。三种办法：

1. 点列表右上角「**刷新**」→ 立刻去 TG 拉一次（等几秒）
2. 等下一轮自动同步
3. 实在不行看日志：`docker logs tgpan 2>&1 | grep DIALOG`

> 前提是这个 TG 小号**真的关注了**那个频道。光收藏没用，要加入。

**Q：扫描时提示「找不到频道」？**
这个 TG 小号还没加入那个频道。先去 TG 里加入（公开频道直接点；私密频道要有人拉你）。

**Q：手动填频道 ID 还能用吗？**
能。接口 `POST /api/scan/channel` 依然接受 `channelId` 字段，列表只是更方便的入口。

**Q：扫描后网盘里没看到文件？**
1. 看扫描结果弹窗，`imported` 是不是 0
2. 如果 `skipped` 很大，可能是消息里的不是视频（照片、文本会被跳过），或者文件太小（<1MB 默认过滤）
3. 刷新页面（F5）

**Q：能扫私密频道吗？**
可以，只要那个小号在频道里就行。

**Q：频道里几万条消息，能全扫吗？**
能。**现在默认就是增量的** —— 记住上次扫到的位置，下轮只拉新消息，
重复点「扫描」也不会从头再翻一遍。

**Q：点了扫描没反应 / 一直转圈？**
多半是撞上 TG 限流（`FLOOD_WAIT`）。程序会**自动等待**要求的秒数再继续，
日志里能看到 `FLOOD_WAIT` 字样。等一会儿就好，别狂点。

**Q：数据会丢吗？**
不会。数据库、TG 会话、配置全在 `/data`（你映射的目录）里。删容器重建数据还在。

**Q：外网访问怎么办？**
飞牛自带的远程访问可以。如果嫌卡，可以用 Cloudflare Tunnel 等方案（后续可加）。

## 技术架构

```
┌──────────────────────────────────────────┐
│  容器 tgpan                              │
│                                           │
│  ┌────────────────┐   ┌────────────────┐ │
│  │  Teldrive      │◀──│ PostgreSQL 17  │ │
│  │  :8080         │   │ + pgroonga     │ │
│  │  连TG/切片/302  │   │ :5432          │ │
│  │  Web UI + API  │   └────────────────┘ │
│  │  + 频道扫描     │                       │
│  └────────┬───────┘                       │
└───────────┼───────────────────────────────┘
            │ MTProto
      Telegram 服务器
```

- **Teldrive**（开源，Go）：连 TG、文件切片存储、文件流、302 直链、Web 界面
- **PostgreSQL + pgroonga**：元数据与全文搜索（硬依赖）
- **频道扫描**（本项目改造）：把频道已有消息登记成网盘文件的索引

> 详细技术说明见 [`docs/TECH-NOTES.md`](docs/TECH-NOTES.md)
